# S3.16: Rust engine 2.0.0, Phase B fixes

S3.16 is the first balance version of the Rust engine (`RACE_ENGINE_VERSION`
`2.0.0`, rewrite plan D2). It is the faithful S3.15 port (Phase A, gate G1)
plus the Phase B fixes F1–F13 (plan §3 Phase 6). The fixes remove TS
accidents (locale-dependent id order, race ids inside RNG labels, stale
caches, float-sensitive comparators, dead knobs); none of them is balance
tuning.

The S3.15 behaviour stays available: building race-core with the `ts-compat`
feature restores every quirk the fixes remove, so the G1 oracle corpus, the
white-box test ports and the pinned `tsCompat` digests keep passing
unchanged. The default (shipped) build is S3.16.

## How each fix is measured

Every fix is its own commit with a paired Rust-vs-Rust report below:

```fish
cargo build -p race-cli --release --locked
target/release/race-cli balance run --out after.json        # 300 races
target/release/race-cli balance compare before.json after.json --title "F<n> ..."
```

The corpus (`balance-v1`, `crates/race-cli/src/balance.rs`) is fixed and
production-shaped: 300 races, lobbies of 8/10/12/14 numeric player ids, a
random two-item loadout for every duck, every Chaos card in turn (NORMAL
twice), and the production pickup config of `lib/season3-race.ts` with
`goldenBoxProbability` left to the resolver default. "Before" is the
previous commit's run, so the reports chain from the baseline (the merge
`8a5b131`: the Phase A port in its default build, i.e. libm maths, byte-order
ids and the 0.15 default) to S3.16. Raw runs are in `artifacts/balance-s3-16/`
(gzip JSON, one per step).

A "bit-identical" race has the same finishing order, the same finish-time
bits, the same final tick and the same number of lead changes. Lead changes
count the ticks on which the rank-1 duck changes. With ~70 ducks per loadout
pair, the per-pair win rates are noisy (±4 pp); item and temperament rows
pool ~700–800 ducks each.

The 42 pinned determinism cases (`crates/race-core/tests/fixtures/
determinism-pinned.json`) are re-pinned for the default build in every
commit that changes simulation output (`race-cli corpus pin`); the `tsCompat`
digests never change (`race-cli --features ts-compat corpus pin --check`).

## Per-fix reports

### F1: byte-order ids

*S3.15:* ids were ordered with `localeCompare` (ICU root collation of the
host locale): punctuation before digits, case only a tertiary difference.
*S3.16:* byte order (`Ord for str`) everywhere an id breaks a tie (sim,
items, pickups, auto-use, Chaos rules), selected in `sim::id_cmp` and
`chaos.rs`. D6 already limits ids to `^[0-9A-Za-z_:-]{1,64}$` at parse time
(every id field is a validated newtype, so `resolve()` can never see an
invalid one; `race-protocol` tests `player_ids_follow_d6`,
`ids_order_by_bytes`). Production player ids are decimal user ids, on which
ICU and byte order agree, so this fix changes nothing for real lobbies; it
only matters for lab/tooling ids such as `p:1` vs `p1` or `B` vs `a`
(test `phase_b.rs::f1_*`). The Phase A default build already used byte
order, so the paired run is unchanged by construction.

Paired run on `balance-v1/300`: races with bit-identical outcomes: 300/300; different winner: 0/300; different finishing order: 0/300.

### F2: no race id in engine RNG labels

*S3.15:* seven engine streams carried the race id (`temperament:<raceId>:<playerId>`,
`auto-use-delay:<raceId>:…`, `auto-use-cooldown:<raceId>:…`,
`pickup-spawn:<raceId>`, `gold-box:<raceId>`, `hazards:<raceId>`,
`pickup-loot:<raceId>:<pickupId>:<playerId>`), so renaming a race or
re-running a week as a new `Race` row reshuffled temperaments, box layouts,
hazards, loot and AI reaction times. *S3.16:* `rng::engine_stream` drops the
race id (`temperament:<playerId>`, `pickup-spawn`, …); the outcome is fixed
by seed and config alone (D5, C17). The Season meta streams (`chaos:week:N`,
`chaos:manual:N:<ms>`, `auto-loadout:<id>`) never carried a race id and are
untouched, and the per-duck `duck:<playerId>` / `track:start` streams never
did either. Tests: `phase_b.rs::f2_*` (a renamed race keeps its motion and
standings in S3.16 and changes them in ts-compat).

Every race draws new temperaments and pickup layouts, so every finishing
order changes; that is a reseed, not a balance shift. The aggregates stay
inside the corpus noise (item rows ±2.2 pp, temperaments ±1.6 pp; the
loadout-pair cells move up to 11 pp, consistent with ~70 ducks per cell).

### F3: one goldenBoxProbability default

*S3.15:* three `goldenBoxProbability` defaults coexisted: Zod's 0.12 (what
TS races actually ran), the engine's unreachable 0.18 fallback
(`pickups/config.ts:5`) and the Rust resolver's 0.15. *S3.16:* the
resolver's `DEFAULT_GOLDEN_BOX_PROBABILITY` (0.15) is the only default; the
engine constant is gone. `resolve_ts_compat` keeps Zod's 0.12 for the
oracle. Tests: `phase_b.rs::f3_*` (omitting the key equals passing 0.15).
The balance corpus already left the key to the resolver, so the paired run
is unchanged by construction.

Paired run on `balance-v1/300`: races with bit-identical outcomes: 300/300; different winner: 0/300; different finishing order: 0/300.

### F4: per-tick caches

*S3.15:* the director's `readRace` memo and `ChaosUtility.observe` were
keyed by float fingerprints (`length + Σ progress·(i + k) + finished`).
The ChaosUtility fingerprint ignores `currentRank`, so after a re-rank with
unchanged progress (stunned or finished ducks) it reused an order built from
older ranks, and any fingerprint collision reused a stale read. *S3.16:*
both memos are keyed by their exact inputs (progress bits, finished flag
and, for ChaosUtility, `currentRank`, in `ducks` order); since inputs are
fixed within a tick, each is a per-tick cache that can never return a read
the current ducks would not compute. Tests: `phase_b.rs::f4_*` (a rank-only
change flips `isLosingNow` in S3.16 and not in ts-compat).

### F5: ghosts out of the in-sim ChaosUtility ranking

*S3.15:* `ChaosUtility` ranked every duck, ghosts included, although the
real Chaos rule only ever sees the non-ghost standings (`sim::result`). A
ghost between two real ducks shifted the projected loser set: the AI of a
duck that was really second to last thought it was safe, and vice versa.
*S3.16:* the in-sim ChaosUtility (both `chaos` and `naiveChaos` of the
objective) leaves ghost ids out of its ranking
(`ChaosUtility::without_ghosts`, a no-op under ts-compat). Tests:
`phase_b.rs::f5_*`. The balance corpus has no ghost ducks (production
lobbies only get one for the occasional ghost race), so the paired run is
unchanged; the fix only matters in ghost races.

Paired run on `balance-v1/300`: races with bit-identical outcomes: 300/300; different winner: 0/300; different finishing order: 0/300.

### F6: squared-distance collector comparator

*S3.15:* the pickup collector ranked contacts by
`Math.hypot(Δprogress, Δlateral)`, so the winner of a contested box
depended on V8's Torque `hypot` (the reason `js_math` exists). *S3.16:*
contacts compare the squared distance `Δprogress² + Δlateral²`
(`pickups::collect::collector_distance`); `EngineMath::hypot2` only exists
under ts-compat, so the default-build sim has no `hypot` at all (the
render-only `track.sample` still uses libm's). Squaring is monotonic, so
only exact rounding ties could differ. Test:
`collect::tests::f6_squared_distance_orders_like_hypot`.

Paired run on `balance-v1/300`: races with bit-identical outcomes: 300/300; different winner: 0/300; different finishing order: 0/300.

### F7: >= for TAILWIND/MAGNET end events

*S3.15:* `TAILWIND_ENDED` / `MAGNET_ENDED` fired only when
`tick === untilTick`, so a window whose end tick was never visited by the
pickup system emitted no end event (the effect itself always ended, since
every reader tests `tick < untilTick`). *S3.16:* the end test is
`tick >= untilTick` and the window is cleared to 0 when it fires, so the
event fires exactly once (`pickups::engine::effect_ended`). The engine
visits every tick while a window is open, so no corpus race changes;
the fix makes the event robust to future step-order changes. Test:
`pickups::engine::tests::f7_*`.

Paired run on `balance-v1/300`: races with bit-identical outcomes: 300/300; different winner: 0/300; different finishing order: 0/300.

### F8: late wild-item inputs rejected

*S3.15:* `queueWildItemInput` clamped a late `authoritativeTick`
(`<= state.tick`) up to the next tick, so an input landed on a tick the
client never asked for and the client's prediction diverged silently.
*S3.16:* `sim::queue_wild_item_input` returns
`Err(LateWildItemInput { at_tick, tick })` and queues nothing; an absent
tick still means the next one, and ts-compat keeps the clamp. Recorded
inputs replayed through `SimOptions::manual_inputs` are unaffected. The
balance corpus has no manual inputs (the Rust server answers the wild-item
POST with 410), so the paired run is unchanged. Test: `phase_b.rs::f8_*`.

Paired run on `balance-v1/300`: races with bit-identical outcomes: 300/300; different winner: 0/300; different finishing order: 0/300.

### F9: dead knobs removed

*S3.15:* six config knobs never changed a race:
`itemTuning.bananaKnockbackMultiplier` and `bananaSlowMultiplier` (parsed,
never read), `itemTuning.rocketSlowMultiplier` (copied onto every rocket's
`slowMultiplier`, which no hit ever read: a rocket hit staggers with its own
constants; the race lab's slider did nothing), and
`pickupConfig.manualItemsEnabled`, `chaosBoxEnabled` and
`idealManualPlayerIds` (server/telemetry fields the engine never reads).
*S3.16:* the resolved config (and so `engineConfigJson`) no longer carries
them; the input still accepts and range-checks them for wire
compatibility, and ts-compat keeps them (through the new race-protocol
feature `s3-15-config`, which only race-core's `ts-compat` enables, so the
config shape always matches the engine; race-cli's own `ts-compat` on
race-protocol still only adds `resolve_ts_compat`). The dead `RocketRuntime`
`slowMultiplier`/`slowDurationSeconds` fields are gone in both builds (no
output read them). `crates/race-core/tests/dead_knob.rs` perturbs each of
the 12 remaining `itemTuning`/`pickupConfig` knobs and requires a changed
race on one of three seeds, and fails when a new knob has no case. The
generated bindings (`PickupConfig.ts`, `RaceItemTuning.ts`) follow. No
simulation output changes.

Paired run on `balance-v1/300`: races with bit-identical outcomes: 300/300; different winner: 0/300; different finishing order: 0/300.

### F10: typed boost-start metadata

*S3.15:* the Nitro start (`startProgress`/`startRank`) was read back from
the start event's untyped metadata with `Number(...)`, only for NITRO and
only when present, and never cleared, so the natural `*_ENDED` event of a
later Draft Fin, Paddle Burst or queued Nitro reported the *previous*
Nitro's start (`items/engine.ts:430-449`). *S3.16:*
`items::engine::record_boost_start` sets both from the typed
`SpeedStartExtras` of the boost being applied, every time (absent for any
boost but a direct Nitro, including queued starts), so an `*_ENDED` event
only carries its own boost's start. The fields only feed event metadata,
so motion is unchanged; the event stream (and the pinned event digests)
change. Test: `tests/boost_start.rs`.

Paired run on `balance-v1/300`: races with bit-identical outcomes: 300/300; different winner: 0/300; different finishing order: 0/300.

### F11: Chaos group validation

*S3.15:* `chaosConfig.groups` was accepted as given: an empty DUO group
averaged `0/0 = NaN` (and then sorted however V8 sorts NaN), a player in
two groups was counted twice by the DUO/CONSTRUCTORS rules and the team AI,
and a group could name a player who was not in the race. *S3.16:*
`resolve()` rejects such configs with `ChaosGroupEmpty`,
`ChaosGroupForeignPlayer` or `ChaosGroupOverlap`
(`race_protocol::config::validate_chaos_groups`); `resolve_ts_compat`
still accepts them, so the oracle keeps the S3.15 behaviour. Groups made by
the Season meta (`chaos::prepare`) are always disjoint lobby partitions, so
no real race changes. Test: `race-protocol/tests/ids_config.rs::chaos_groups_are_validated`.

Paired run on `balance-v1/300`: races with bit-identical outcomes: 300/300; different winner: 0/300; different finishing order: 0/300.

### F13: Feather copy and matrix aligned with the code

*S3.15:* the loadout Feather's copy promised a dodge of "Vỏ Chuối, Còi
Quack Horn hoặc chướng ngại vật", and `ITEM_INTERACTION_MATRIX` marked the
Feather column `Dodge` for `MINOR_HAZARD`, but the loadout Feather only
ever dodges bananas (`resolve_incoming_race_effect`) and the Quack Horn
(`auto_use::execute`); hazards are dodged only by the wild Feather Hop.
*S3.16:* the catalog copy (`catalog::FEATHER_DESCRIPTION`, served by the
Rust server's item list) reads "nhảy né 1 lần Vỏ Chuối hoặc Còi Quack Horn
(không chặn Tên Lửa hay chướng ngại vật)", the rules page copy
(`src/season3/season3-rules-content.ts`) matches, and the matrix marks the
hazard cell `No`. The Guard Surge (+15% for 1.8 s) and glide (+4% for 1 s
from 88%) numbers already matched `items::config`. ts-compat keeps the
S3.15 text and matrix (meta parity compares the catalog with TS). Display
data only. Tests: `phase_b.rs::f13_*`.

Paired run on `balance-v1/300`: races with bit-identical outcomes: 300/300; different winner: 0/300; different finishing order: 0/300.
